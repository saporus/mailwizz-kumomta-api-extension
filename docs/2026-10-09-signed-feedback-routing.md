## Authentication, correlation and durable acknowledgement

Any bounce or complaint arriving at an endpoint listed in a policy binding must identify the configured tenant and authenticate the exact raw body with that binding's existing HMAC secret. Disabled, unknown or ambiguous bindings fail closed. Authentication does not bootstrap the app or access a database. Genuinely unbound endpoints retain the existing single-server legacy path; a failed configured binding cannot downgrade to it.

Signed bounces require `webhook_event_id`, campaign, message ID and recipient. `event_id` may be an original Message-ID and is never substituted for webhook event identity. No payload server ID grants authority. The native proof is a unique successful delivery tuple containing server, trusted customer, campaign, list and subscriber identity, exact normalized recipient, and exact message ID with optional angle brackets. Both current and archive tables are checked. Identical archived copies collapse to one tuple; different servers or subscribers remain ambiguous and return409 without effects.

One transaction on the existing Yii/PDO connection locks the exact native subscriber row with `SELECT ... FOR UPDATE` before fresh native reads, deduplication, persistence and protection. Both signed bounce and complaint paths use that row lock. Current failed effects roll back and remain retryable503; a previous durable partial effect can be repaired on retry. Process loss releases the database lock. No blind resend or callback replay is introduced. Soft-to-hard reclassification remains an explicit409 conflict, not an automatic historical change. Unbound legacy callbacks preserve their preexisting persistence behavior and do not gain this signed-path transaction.

Signed complaints invoke the configured native FBL action within that transaction. Blacklist requires durable blacklisted status and a complaint row; customer-only blacklist also requires that customer's blacklist row and never escalates to global blacklist. Unsubscribe requires durable unsubscribed status, unsubscribe tracking and a complaint row; it does not blacklist. Native ignored write failures cannot produce200. An already-unsubscribed partial result can repair only its authenticated campaign's missing tracking records. Exact complete duplicates return200 without repeating the native action. The delete setting destroys correlation evidence and therefore returns503 without deletion until a separate durable receipt design exists. At 14:54:49 UTC the production setting was blacklist, not delete. Unbound legacy complaint behavior is unchanged.
