## Authentication, correlation and durable acknowledgement

Disabled, unknown or ambiguous bindings fail closed. Authentication does not bootstrap the app or access a database. Genuinely unbound endpoints retain the existing single-server legacy path; a failed configured binding cannot downgrade to it.

Signed bounces require `webhook_event_id`, campaign, message ID and recipient. `event_id` may be an original Message-ID and is never substituted for webhook event identity. No payload server ID grants authority. Both current and archive tables are checked. Identical archived copies collapse to one tuple; different servers or subscribers remain ambiguous and return409 without effects.

## Shared webhook rules for additional delivery servers

Code review after the user authorized the separate engine445 update confirms that a new MailWizz delivery server does **not** inherently require another Kumo tenant webhook. An existing signed `/dswh/433` ingress can serve several explicitly authorized delivery-server IDs. This section records code behavior, not a claim that every row on the backend delivery-server index has been verified or added.

- The callback endpoint ID must itself occur in a configured binding. The payload tenant selects exactly one enabled binding for that endpoint, and the exact raw body must authenticate using its existing webhook HMAC secret. A tenant API key is not the webhook signing secret. Missing/invalid signatures cannot fall back to legacy routing.
- The binding's trusted MailWizz customer must own the correlated campaign. The sender's delivery-server ID must be explicitly listed. A shared hostname, display name, global server row or campaign customer alone grants no authority to another server.
- Signed bounce/complaint callbacks require a stable `webhook_event_id`, campaign ID/UID, original Message-ID and recipient. A unique successful native tuple across current/archive logs must match that campaign, customer, list/subscriber, normalized recipient and a listed server. The incoming server ID cannot select authority; ambiguous or unmatched tuples fail without effects.
- Different enabled API keys belonging to the same Kumo tenant can share the hook. The receiver does not use `api_key_id` to authorize a MailWizz server, so key/SMTP-credential tenant ownership must be independently verified before extending the binding. Different customers or tenants require their own trusted binding/scope; they must not be merged merely because they use the same Kumo host.
- Ordinary signed bounce/complaint correlation reads the MailWizz binding and tenant hook signature, not the engine policy bridge's server list. The445 live readback demonstrated this before the engine list update. Complete recipient-policy integration additionally requires matching explicit bridge/customer/server IDs and secret configuration on both sides, followed by a new signed readiness verification. Changing IDs invalidates the old engine verification fingerprint; it must not be reused.
